# Известные проблемы ip-manager

Результаты ревью версии 1.3.5 (ноябрь 2026). Проблемы C1 и C2 исправлены в 1.3.6 (коммит `40fb924`), всё остальное ниже пока открыто.

Места в коде указаны по **именам функций**, а не по номерам строк: номера сдвигаются. Python-хелперы (`cmd_*`) встроены в `ip-manager.sh` и вызываются через `pyip`.

Как продолжить работу: передать этот файл в новый чат вместе с фразой «исправь H2» (или другой ID).

## Порядок исправления

1. **H2.** Случайный выбор адресов может забрать IP соседей.
2. **H1.** Glob-match в netplan навешивает IP на все сетевые карты.
3. **M3.** После перезагрузки меняется исходящий IP (ifupdown).
4. **M5 и M7.** NM проглатывает ошибки, нет отката при прерывании.
5. **M2.** Выбирается бэкенд, который на самом деле не работает.
6. Остальное: H3, M1, M4, M6, M8, L1–L6.

Открытые вопросы к владельцу (от ответов зависит объём M1 и M5):
- Бывают ли дополнительные IP больше чем на одном интерфейсе одного сервера?
- Есть ли серверы с NetworkManager, или везде netplan/networkd и ifupdown?

## High

### H1. Glob- или driver-match в netplan навешивает IP на все подходящие карты
- **Где:** `detect_netplan_identity`, внутренняя проверка `matches()`.
- **Когда срабатывает:** в netplan есть `match: name: "en*"`, `match: driver: …` или другой шаблон, а на сервере 2 и больше сетевых карт (например, публичная и приватная).
- **Что происходит:** код проверяет только, что определение подходит к `$IFACE`, и не проверяет, что оно подходит *только* к нему. Overlay добавляет адреса в это определение, и netplan генерирует `[Match] Name=eth*` + `Address=…`. После перезагрузки или рестарта networkd публичные IP и policy routes оказываются на **каждой** подходящей карте.
- **Проверено:** воспроизведено на Ubuntu 24.04, 20.04 и Debian 12 (по сгенерированному `.network`).
- **Как исправить:** отказывать, если в match есть glob или ключ `driver`, либо если match подходит больше чем к одному интерфейсу из `/sys/class/net`.
- **Как воспроизвести:** `ethernets: all-eth: match: {name: "eth*"}`, вторая карта `eth1`. В `10-netplan-all-eth.network` появляется `Name=eth*` + `Address=203.0.113.10/32`.

### H2. `--random --from <подсеть основного IP>` раздаёт IP соседей
- **Где:** `cmd_plan_add`, ветка random (Python-хелпер), вызывается из `do_add`.
- **Когда срабатывает:** `add --random N --from </24 основного IP>` (или та же подсеть в меню) на любом VPS с общей L2-сетью.
- **Что происходит:** зарегистрировать подсеть, в которой лежит основной IP, скрипт не даёт, а взять из неё случайные адреса позволяет. В итоге он выдаёт IP соседей: ARP-конфликты, другие клиенты хостера теряют связь, хостер может заблокировать порт. В предупреждении скрипт сам советует `subnet add <эта подсеть>`, но такую команду он же и отклоняет.
- **Проверено:** воспроизведено. `plan_add --random 3 --from 172.17.0.0/24` при основном IP 172.17.0.2 выдал `.9`, `.12`, `.162`.
- **Как исправить:**
  - отклонять `--from` и явные `/NN`, если они пересекаются с сетью основного IP;
  - для `--random` разрешать только зарегистрированные подсети;
  - дополнительно проверять каждый адрес на занятость через `arping -D` перед добавлением.

### H3. Self-update без проверки подлинности и с возможностью отката версии
- **Где:** `self_update`, `install.sh`.
- **Когда срабатывает:** на любом сервере.
- **Что происходит:** код для root скачивается с изменяемой ветки `main` и проверяется только через `bash -n`. Если аккаунт или репозиторий GitHub скомпрометирован, злоумышленник получает root на всех VPN-нодах. Версии сравниваются через `!=`, поэтому, если CDN raw.githubusercontent отдаёт закешированный старый файл, скрипт **откатывается** (например, «обновлён v1.3.5 → v1.3.4»).
- **Проверено:** по коду.
- **Как исправить:**
  - публиковать релизы под тегами с подписанным SHA256 (minisign или GPG с ключом, встроенным в скрипт);
  - отказывать, если удалённая версия ниже локальной (`sort -V`).

  Перед этим нужно решить, как публиковать релизы.

## Medium

### M1. При нескольких интерфейсах overlay перезаписывается
- **Где:** `render_persistence` + `managed_for_iface`.
- **Когда срабатывает:** сервер с несколькими сетями, где маршрут по умолчанию переехал или интерфейс по умолчанию сменился после переустановки.
- **Что происходит:** единственный файл overlay генерируется только для текущего `$IFACE`. Управляемые IP другого интерфейса молча пропадают из постоянного конфига, хотя в `managed.tsv` остаются.
- **Проверено:** воспроизведено (по выводу render).
- **Как исправить:** генерировать overlay для всех интерфейсов, у которых есть управляемые IP, либо отказывать, если в state есть строки для другого интерфейса.

### M2. Netplan выбирается, даже когда его renderer не работает
- **Где:** `detect_backend`.
- **Когда срабатывает:** на сервере остались `/etc/netplan/*.yaml`, а сеть реально управляется ifupdown или NM (или networkd выключен).
- **Что происходит:** netplan побеждает, как только он *объявляет* интерфейс, даже если его renderer не запущен. IP записываются в файлы networkd, которые никто не читает, и пропадают после перезагрузки.
- **Проверено:** воспроизведено (Debian 12 + ifupdown → `BACKEND=netplan`).
- **Как исправить:** требовать, чтобы renderer netplan реально использовался. Для networkd: `networkctl status` показывает `Network File: …netplan…`. Для NM: профиль называется `netplan-*`. Иначе отказывать.

### M3. ifupdown: после перезагрузки меняется исходящий IP
- **Где:** генерация для ifupdown в `render_persistence`.
- **Когда срабатывает:** Debian с ifupdown (стандартная строка `source /etc/network/interfaces.d/*` стоит *выше* основного stanza), основной IP /32 с on-link шлюзом, или дополнительные IP в подсети основного.
- **Что происходит:** при загрузке наш stanza `inet manual` выполняется **раньше** основного, поэтому дополнительные адреса добавляются первыми. Ядро выбирает первый из них исходящим для всего трафика. Ломаются whitelist у хостера, привязка IP в Remnawave и видимый адрес ноды. При следующем запуске ip-manager ещё и принимает этот дополнительный IP за «основной».
- **Проверено:** воспроизведено (порядок в `ifup -n`, `ip route get` показывает `src` = дополнительный IP).
- **Как исправить:**
  - добавлять адреса через `up ip address add …` из stanza, который идёт после основного, либо через `post-up`;
  - или ставить `preferred_lft 0` на дополнительные адреса и явно задавать `src` в маршруте по умолчанию;
  - плюс в `detect_network` проверять, что `PRIMARY_IP` не входит в управляемые IP, а если входит, отказывать.

### M4. Netplan overlay не самодостаточен
- **Где:** генерация netplan в `render_persistence`.
- **Когда срабатывает:** провайдер или cloud-init переименовал или удалил определение (ID VLAN или bond). На Cherry с bond0 похожее уже случалось.
- **Что происходит:**
  - `vlans: X: addresses` без самого определения не проходит `netplan generate` («missing 'link'»), и при загрузке **сеть не настраивается вообще**;
  - оставшийся `ethernets: <старое имя>` может создать второй `.network`, который сортируется раньше нужного.
- **Проверено:** воспроизведено (ошибка generate).
- **Как исправить:** при каждом запуске проверять, что `NETPLAN_TYPE`/`NETPLAN_ID` есть в итоговой модели и без нашего файла. Если нет, громко предупреждать или отключать overlay.

### M5. NetworkManager: ошибки `nmcli` проглатываются
- **Где:** `persist_nm` (вызывается внутри контекста `if !`, поэтому `set -e` не действует).
- **Когда срабатывает:** на бэкенде NetworkManager.
- **Что происходит:** ошибка `nmcli +ipv4.addresses` теряется, а функция возвращает результат `verify || true`. Это тот же механизм, что в C1. Кроме того, нет защиты от профилей, сгенерированных netplan в `/run` (запасной вариант, когда нет PyYAML или `netplan get`), и от профилей, которые живут только в памяти. Такие профили пропадают после перезагрузки.
- **Проверено:** по коду.
- **Как исправить:**
  - проверять результат каждого вызова `nmcli`;
  - читать `FILENAME` через `nmcli -f` и отказывать, если файл лежит в `/run` или профиль называется `netplan-*`.

### M6. Файлы networkd в `/run` считаются постоянными
- **Где:** `detect_networkd_identity`.
- **Когда срабатывает:** `.network` лежит в `/run/systemd/network` и создан не netplan, а `systemd-network-generator` из `ip=` в параметрах ядра, некоторыми PXE или initramfs.
- **Что происходит:** drop-in пишется в `/run/...network.d/` и пропадает после перезагрузки.
- **Проверено:** по коду.
- **Как исправить:** всегда класть drop-in в `/etc/systemd/network/<name>.network.d/`.

### M7. Нет отката при прерывании и нет проверки расхождений
- **Где:** trap в `init`, `do_add`, `do_delete`, `import_ips`, `subnet_add`, `commit_config`.
- **Когда срабатывает:** Ctrl+C, обрыв SSH (SIGHUP) или SIGTERM посреди операции.
- **Что происходит:**
  - есть только trap на EXIT, отката нет;
  - постоянный конфиг и state могут содержать IP, которых нет в runtime, а файлы `.prev` остаются лежать;
  - `list` и `check` показывают только *runtime*, поэтому такое расхождение (как и потери в стиле инцидента #1) не видно.
- **Проверено:** по коду.
- **Как исправить:**
  - на время критической секции игнорировать INT/HUP/TERM либо откатывать изменения в trap;
  - добавить в `list` и `check` сверку state ↔ overlay ↔ runtime.

### M8. Номера таблиц маршрутизации совпадают с tproxy
- **Где:** `alloc_table`.
- **Когда срабатывает:** Xray или sing-box с tproxy (таблица 100 по традиции) либо другие инструменты, которые не были запущены в момент регистрации подсети.
- **Что происходит:** свободная таблица ищется только по текущему runtime. После перезагрузки два конфига воюют за одну таблицу.
- **Проверено:** по коду.
- **Как исправить:**
  - дополнительно сканировать конфиги в `/etc` и `rt_tables`;
  - начинать поиск с редкого диапазона (например, 2000+);
  - разрешить указывать таблицу вручную через `--table`.

## Что не удалось проверить

- Используют ли шаблоны Cherry, Hetzner и других провайдеров glob- или driver-match при нескольких картах. От этого зависит H1.
- Перегенерирует ли cloud-init у ваших провайдеров netplan с другим ID при перезагрузке (M4). Azure и некоторые конфигурации EC2 делают это при каждой загрузке.
- Как NetworkManager обходится с адресами из `ip addr add` при продлении DHCP или reapply, и переживают ли перезагрузку профили из памяти и `/run` после `nmcli modify`.
- Переписывают ли OpenVZ (vzctl) и Proxmox LXC `/etc/network/interfaces` при старте контейнера, теряя строку `source`, и разрешает ли OpenVZ вообще добавлять адреса изнутри.
- Где базовый netplan-файл Cherry стоит в порядке сортировки относительно `60-*.yaml` и `90-ip-manager.yaml`. От этого зависит, какой адрес ядро возьмёт основным после рестарта networkd.
- Какие таблицы маршрутизации используют tproxy и другие VPN-инструменты на ваших нодах (M8).

## Тесты, которые стоит добавить

Скрипты, на которых проводилось ревью, лежали во временной папке сессии и могут пропасть. Их подход такой:
- функции загружаются через `sed '$d' ip-manager.sh` (отрезается последняя строка `main "$@"`), затем `set +e`;
- тесты гоняются в Docker-образах Ubuntu 24.04 / 20.04 / Debian 12 с `--cap-add NET_ADMIN`;
- для реального networkd нужен контейнер с systemd.

Что стоит покрыть:

1. **Матрица Docker:** Ubuntu 20.04, 22.04, 24.04 и Debian 11, 12 × бэкенды: netplan→networkd, netplan→NM, чистый networkd, ifupdown, NM.
2. **Переживание рестарта:** в systemd-контейнере добавить IP → `networkctl reload` + `reconfigure` (или рестарт NM, или `ifdown`/`ifup`) → все IP и правила на месте. Такой тест поймал бы инцидент #1 и C2.
3. **Сбои записи:** tmpfs, заполненный на 100%; read-only bind mount; `chattr +i` на каждый целевой каталог. Ожидается ненулевой код выхода, а overlay, state и runtime остаются без изменений.
4. **Точность match:** glob, driver, MAC + `set-name`, bond, VLAN и bridge с двумя картами. Ожидается отказ или ровно одна подходящая карта.
5. **Overlay без файла провайдера:** `netplan generate` проходит, либо скрипт предупреждает при старте.
6. **Свойства планировщика адресов:** никогда не выдаются основной IP, шлюз, адреса сети и broadcast, уже занятые адреса и адреса из подсети основного IP. Отдельно проверить диапазоны через границу /24, /31 и незарегистрированный `--from`.
7. **Сигналы:** SIGINT/SIGTERM на каждом шаге `do_add`, `do_delete`, `import_ips`, `subnet_add`. Ожидается, что state, постоянный конфиг и runtime согласованы, либо `list` показывает расхождение.
8. **Порядок загрузки в ifupdown:** после `ifup` команда `ip route get 1.1.1.1` по-прежнему показывает основной IP как `src`.
9. **Self-update:** версия ниже локальной отклоняется, неверная подпись отклоняется.
10. **Линт:** `shellcheck -S warning` и правило, которое ловит функции с записью на диск, вызываемые из `if`/`!`/`&&`.
